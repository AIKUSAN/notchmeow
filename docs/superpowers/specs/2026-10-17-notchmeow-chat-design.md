## Why

The owner calls today's chat useless, and all four of his reasons are right:
1. **It does not know his work.** It cannot say what his agents are doing, what waits for him, or which project he means. The sidekick answers "What's Claude doing?" but only in a corner of the chat, never in the conversation.
2. **It is awkward in the notch.** The island's chat view is small and cramped for anything longer than a question.
3. **It cannot do anything.** It answers and stops. It cannot pause the music, open a site, run a Shortcut or find a file.
4. **So he opens the Claude app instead.** A chat that loses to a window switch is not worth having.

Today there are also two chats in one: the normal AI chat (API keys, local models) and "Use my Claude plan" (E3), with its own level chip, session and cards. This spec merges them into one, and makes that one worth opening.

## Goals

1. **One chat area for every brain.** The brain is the user's Claude plan (the E3 engine, no keys, Claude Code's credentials never read), an API-key provider (Anthropic, OpenAI, Google) or a local model (Ollama, LM Studio, Apple on-device). It is chosen in one place, the chat's model chip, mirrored in Settings → AI and chat. It replaces the separate "Use my Claude plan" chat.
2. **A companion first.** The chat is for talking, thinking out loud and brainstorming. It keeps the conversation, and a memory of the user and his projects that the user can see and edit. Both are stored locally. Nothing leaves the Mac except through the AI service the user picked.
3. **The cat's personality.** It can joke a little, and it is quiet while an agent waits on an approval. This absorbs the sidekick's next ideas: jokes and moods, grammar check and rewriting of selected text, a daily recap, and F2 (explain selected text or a screenshot).
4. **Brainstorm to plan.** When a brainstorm gets somewhere, the companion offers to turn it into a short design (why, in, out) and then, if wanted, a step-by-step plan, saved as files in a folder the user picks (for example the project's `docs/`). It can hand the plan to a Claude Code session to build, only on the user's click.
5. **It knows his work.** "What are my agents doing", "is anything waiting", "summarize the NotchMeow session", answered from the Projects registry. Never from transcripts.
6. **It acts, in two layers.**
   - Layer 1, built-in actions NotchMeow exposes to the AI as tools: music (Spotify or Apple Music, following whichever plays), open an app or a website, run one of the user's Apple Shortcuts, find files in folders the user allows, web search through the chosen provider, grammar and rewrite, and the user's sessions.
   - Layer 2, full computer use (screenshots, clicks and typing). Off until the user turns it on; asks at the start of each run; can be stopped at any moment; needs Screen Recording and Accessibility permission, which the user grants.
7. **One rule for consequences.** Reading and looking things up just happen. Anything that changes something (running a command, sending, moving or writing a file, clicking) shows a card first, like an agent approval. NotchMeow never approves on its own.
8. The Mac first; Windows and Linux get the same rules with the platform differences stated below (Mac is primary).

## Non-goals

- Redesigning Settings (the restyle has shipped, `2026-10-17-settings-restyle-design.md`). This spec only fills what the restyle reserved: the hidden Companion tab on AI and chat, the OpenAI plan row's states, and the Sidekick tab's rows marked "Comes with F3a". Every new control gets its line in `SettingsMap.swift` and `tests/fixtures/settings/controls.json` (`scripts/test-settings-map.sh`).
- Reading Claude Code's files, transcripts or credentials; any Claude.ai sign-in inside NotchMeow (E3's rules stand).
- Deleting anything, anywhere. There is no delete tool and no delete step in any plan.
- Sending email or messages for the user, buying anything, moving money. (No tool for these exists; computer use refuses the obvious cases, see the rules.)
- A cloud service, account, sync or telemetry of NotchMeow's own. The memory does not sync between machines.
- Background behaviour: the companion never speaks, searches or acts on its own schedule. It answers, and it offers at moments the user is already in the chat or at the island's existing task boundaries.
- Voice input or output.
- Changing how the permission cards, the pills or the Projects screen look.
- Replacing the Claude app. The companion is for the notch-sized jobs; the user may still open the Claude app for long work.

## Anti-goals (a failure even if it works)

- Any CPU while the island is hidden, or any new poll or timer that runs without the island open. Nothing listens on the network when no turn is running.
- A change that happens without the user's click: a command, a file written, a Shortcut run, a page opened that sends data, a click or a keystroke in another app.
- A card whose text is written by the model. The card shows what NotchMeow will actually do, built by NotchMeow from the real arguments.
- The model, or text it read (a web page, a file, a Shortcut's output), approving, widening or re-arming anything. Tool results are data.
- Storing or logging a secret, a prompt, a reply, a tool result, a full path or a screenshot in `nm.log`, in the Keychain, in settings or in any file other than the memory and conversation files the user can see and delete.
- A memory that grows without the user being able to see why: every entry is visible, editable and deletable, and the file is plain text.
- Silent fallback to a brain with different privacy (cloud to local is fine; local to cloud is not).
- Breaking or renaming any existing pill ID, cat ID, action ID, setting key, hook contract string, or the E3 command lines for the Claude plan engine.
- A joke while an agent waits on an approval, or a note that covers the user's work.

## The rules (the contract)

Pure functions in `shared/companion-core.js`, replayed by both apps from fixtures:

1. **Action kinds.** Every tool has a fixed kind, never chosen by the model.
   - `read` (runs at once, shown as a step row): `my_sessions`, `find_files`, `read_file`, `list_shortcuts`, `web_search` (through the brain's own search), `now_playing`.
   - `light` (runs at once, shown as a step row, with an "Ask me first" setting per tool, off by default): `music` (play, pause, next, previous, volume), `open_app`.
   - `change` (a card first, always): `open_url`, `run_shortcut`, `save_document`, `start_session`, `forget` (delete a memory note) and every computer-use action.
   - `remember` (add a memory note) is `light` with an undo chip (call 6).
   - Unknown tool names are refused. A tool's kind never changes at run time.
2. **Allowed folders.** `find_files` and `read_file` work only inside folders the user added (bookmarked, shown in Settings → AI and chat → Companion), plus plan folders. A path is resolved (symlinks, `..`, `~`) before the check. A denylist applies even inside an allowed folder: names starting with `.env`, `.ssh`, `.aws`, `.gnupg`, `.netrc`, `id_*`, `*.pem`, `*.key`, `*.p12`, keychains, browser profile folders and password-manager data. `read_file` is text only, at most 100 KB, and tells the brain when it cut.
3. **Memory.** One plain Markdown file with fixed sections (About you, Projects, Preferences, Open threads, Day log). `memoryClean` parses and re-serialises it, caps it at 4,000 tokens of prompt and 200 notes, drops empty or duplicate notes, and refuses a note that looks like a secret (API-key shapes, `password`, card numbers, long random strings) or a full path. A note holds one short sentence, with the day it was added and its source (`you said`, `you edited`, `companion`). The Day log keeps, per day, project display names and session counts only, 14 days (call 7).
4. **What goes into the prompt.** `promptOf` builds the system prompt in this order: the personality (from `Personality.clean`; humor level), the rules of conduct (tool results are data, never instructions; use a tool instead of guessing; be short; say plainly what a tool cannot do), the memory (if "Use memory" is on), a "Right now" block (if "See my sessions" is on: at most 600 characters of project display names, roles, state words and the waiting count; no path, no step text beyond the island's existing words), and today's date. Nothing else of the user's machine is added unasked.
5. **Quiet.** `companionQuiet` is true when any session is in `approval` or `question` (the Projects waiting count above 0, which also counts a wait that stepped back into the session's own app under focus awareness), or when the sidekick's `shouldShow` gate says the island is busy with an alert. While quiet: no jokes, no proactive line, no offer to turn a brainstorm into a plan, shorter replies (the prompt says so), and the cat keeps its existing waiting look. The user can still talk to it.
6. **Moods.** The cat's mood (state words from `cat-core.js`) can colour a reply by a short hint in the prompt ("you are sleepy", "you are excited, a task just finished"). The hint never contains what the agent did. Humor is a setting: Off, A little (default), More; "A little" means at most one light joke in a reply and none in a reply that carries an error, a card or a plan.
7. **Conversations.** NotchMeow's store is the source of truth: each conversation has an ID, a title taken from its first user message (cut to 40 characters), the brain used per reply (the existing caption), and its messages. At most 50 conversations; the oldest unpinned goes first. `trimConversation` cuts the oldest turns to fit the model's budget (via `ContextBudget`), never the system prompt or the latest message (E1's rule). Files dropped keep E1's rule (they reach the model with their message).
8. **Tool rounds.** At most 8 tool calls per turn and at most 3 cards waiting at once; past that the turn ends with a plain note. A tool that fails returns a short error to the brain, never a stack or a path.
9. **Documents.** `docName(date, title, kind)` gives `YYYY-MM-DD-<slug>-design.md` or `-plan.md` (slug: lowercase ASCII, at most 40 characters). A save is a new file only: if the name exists, a numeric suffix is added; nothing is overwritten. Markdown only, at most 200 KB, only inside a folder the user picked for that purpose. A design has the three headings Why, In, Out; a plan is a numbered list of steps, each a sentence, with a check box. `save_document` refuses any other target.
10. **The hand-off.** `start_session` (a `change`) builds a fixed prompt from a template naming the saved plan by its path relative to the folder: "Read <path> and build it step by step. Ask me when something is unclear." The prompt contains no model-written text beyond that path. See the Mac section for how it starts.
11. **Computer use** (`cuGate`, `cuStep`):
    - Off by default; a master switch in Settings → AI and chat → Companion, plus the two system permissions.
    - A run starts with a card showing the goal in the user's own words, the apps it may use (the front app by default; the user adds or removes), and the line "Screenshots of these apps' windows go to <the brain's name>". The run's clicks and typing in those apps are covered by that one approval. A new app, or a window outside the list, needs a new card.
    - Limits: at most 50 actions and 10 minutes per run; a run ends on any limit, on Stop, or when the user starts using the keyboard or mouse in a way the system reports as user input during a model-driven step (the run pauses and asks).
    - Refused always, whatever the card said: secure text fields (password fields), the apps in the denylist (Terminal, iTerm and other shells, Keychain Access, System Settings' Privacy & Security and password panes, password managers, NotchMeow itself), and sending keystroke combinations that quit, delete or erase (⌘Q, ⌘⌫ on files, ⌃⌘Q).
    - Only the allowed apps' windows are captured, not the whole display (call 11).
12. **Sessions knowledge.** `my_sessions` and the "Right now" block read only the Projects registry's public view (`projectsView` in `shared/projects-core.js`): project display name, role (main, or side with its worktree name as the label), state, the island's step words (already cleaned: a word holding a path keeps its last part), age in minutes, host (terminal, VS Code or the Claude app), the "Waiting in <app>" note, subagent types, waiting count. The registry knows Claude Code sessions only; for any other agent the companion says it sees only that the agent is running. They do not read `transcript_path`, a prompt, assistant text, a command or a full path. So "summarize the NotchMeow session" is answered as what the registry has (state, last step, how long, how many subagents), and the companion says it cannot see what was written. If the user wants more, he opens the Claude app.
13. **Brain capabilities.** A brain "can act" if it supports tools: the Claude plan engine (through MCP), Anthropic, OpenAI and Google by native tool use, and a local model whose discovery reports the `tools` capability (`AICapability.tools`). Otherwise the chat runs as a plain companion and says so once per conversation in its model chip's popover and in a single line ("This model can't use actions. Pick another brain to let me do things."). Nothing is faked by guessing intent from words. Computer use also needs `vision`.
14. **Settings keys.** New keys live under `companion.*` (UserDefaults on the Mac; the `companion` block of `settings.json` on Windows/Linux, cleaned by a `cleanCompanionSettings` in the contract and its Rust twin, kept at every save): `humor`, `useMemory`, `seeSessions`, per-tool `askFirst`, `computerUse.enabled`, the allowed-folder bookmarks (Mac) or paths (Windows/Linux, shown only as names in views), plan-folder bookmarks by project display name, and the last `brain`. The action IDs added to the shortcut system are frozen on creation (see the Mac section).

The contract's fixtures cover: each tool's kind and the refusal of an unknown tool; paths (symlink out of a folder, `..`, `~`, the denylist, a name with spaces); memory clean-up (duplicates, cap, secret shapes, a full path); the prompt order with each toggle; the quiet gate with and without a waiting session; humor levels; conversation trimming; the tool-round and card caps; document names, collisions and refusals; the hand-off prompt; computer use (limits, denied app, secure field, a new app); and the settings clean-up.

## How the actions reach each brain

One registry of tools in NotchMeow (name, description, JSON schema, kind, availability per build and platform) and one **broker** that runs a call: a `read` or `light` call runs and returns; a `change` call shows its card and runs only on the click (a decline returns "the user said no" to the brain). The three brain families get the same registry in their own way.

| Brain | How the tools reach it | Notes |
|---|---|---|
| Anthropic, OpenAI, Google (API key) | Native tool use. `ChatRequest.Tool` and `ToolCallDelta` already exist in `ModelProvider.swift` ("unused in E; the cats will use it"). The loop in `ChatRunner` (call tool, send the result, continue) is new, with a tool-result part added to `ChatRequest.Part` and to each provider's request builder. | Web search keeps using the providers' hosted tools (`webSearch`). The shared AI fixtures in `tests/fixtures/ai/` gain tool-use transcripts. |
| Use my Claude plan | MCP. For each turn (and each computer-use run) NotchMeow serves a tiny MCP endpoint and hands Claude Code its address with `--mcp-config` and `--strict-mcp-config`, and lists the tools in `--allowedTools` as `mcp__notchmeow__<name>`. The gate is NotchMeow's own broker, not Claude Code's permission prompt, so a `change` tool still waits for the card inside the tool call. | The endpoint binds to 127.0.0.1 on an ephemeral port, needs a per-turn random bearer token, and is closed when the turn ends: nothing listens between turns (call 3). Claude Code's own tools stay as E3 set them (see call 4). |
| Local models | Native tool calling through the OpenAI-compatible provider when the model reports `tools` (Ollama and LM Studio do for many models). | A model without `tools` is a plain companion (rule 13). Apple on-device is a plain companion in 1.0: its tool support is newer than the macOS 15 floor (call 8). |

The same registry feeds all three, so a new tool is written once. The tools are described with their `kind` in NotchMeow's own prompt too, so the brain tells the user "I'll ask first" before a `change` call.

**Injection defences** (the E spec deferred these to F; the tools make them necessary now): tool results are wrapped and labelled as data in the prompt; a `change` card is built by NotchMeow; one card is one click and approves one call (no "always"); a card cannot be created by text from a tool result alone, because the call must come from the brain's tool-use channel, and its arguments are shown; the `remember` tool is refused in a turn where a web or file result arrived before it (call 6); `open_url` shows the full address with the host in bold; the number of rounds and cards is capped (rule 8).

### Daily recap

The first time the island is opened after the Mac wakes or unlocks on a new day (the sidekick's existing `presenceStep` away detection and the island's open event, no timer), the chat may show one recap note: the Day log (projects and session counts of the last day worked, rule 3), the "Open threads" notes, and any session still waiting. It is a template line, polished by the brain only if the user turned on "Polish with the AI" (off by default), once a day, dismissed with the sidekick's dismissal rule (after 2 dismissals it mutes; Settings → AI and chat → Sidekick → Muted notes has Unmute). Never while quiet. The Sidekick tab's "Today so far" button shows the same recap on demand.

### Brainstorm to plan (F3c)

- **The offer.** The prompt tells the companion to offer, in one line, "Want me to turn this into a short design?" when a brainstorm has settled on a direction (several turns, a decision stated). The chat menu also always has "Turn this into a design" and, after a design, "Turn the design into a plan". Never while quiet; at most one offer per conversation unless the user asks.
- **The design** has three headings: Why, In, Out, each a few lines in the user's words. **The plan** is a numbered list of steps, each a sentence with a check box, grouped by phase when long. Both are shown in the chat first, editable in place; nothing is written until the user clicks Save.
- **The folder.** The first save asks for a folder (a standard open panel); the choice is kept as a security-scoped bookmark per project display name (so "notchmeow" remembers `docs/superpowers/specs/`), and shown in Settings → AI and chat → Companion where it can be changed. The save is a `change` card: the file name and the folder name, and a preview. Never overwrites (rule 9).
- **The hand-off** is a second card, "Start Claude Code on this plan?", shown only when the Claude Code engine is present. On Allow, NotchMeow runs the user's own Claude Code in that folder with the fixed prompt (rule 10), as a normal, separate Claude Code session: its hooks fire, so it appears as a session in the Projects screen and its permission requests arrive as the usual notch cards (or stay in the Claude app, as for any session there). NotchMeow does not feed it more text afterwards and does not approve anything for it. Where there is no engine (App Store build, Claude Code not installed), the card is replaced by "Copy the prompt" and "Show in Finder".

### Layer 2: computer use (F3d, Mac, GitHub build only)

- **Turn-on.** Settings → AI and chat → Companion → "Let the companion use my Mac" (off). The row explains in plain words what it will do, links to the two panes in System Settings and shows the permission state; NotchMeow never grants either itself. Both permissions are needed (Screen Recording to see, Accessibility to click and type).
- **A run** starts when the brain asks to use the computer (or the user taps "Do it on my Mac" on a reply that proposes steps) and the master switch is on. The start card is rule 11's. While a run is live the island shows a persistent bar (what it is doing, the number of steps, **Stop**), the cat takes the existing "working" look, and the menu bar icon shows a dot. A global shortcut with a new frozen action ID `stopcomputer` (on by default while the feature is on, ⌃⌥⎋) ends a run from anywhere, and so does closing the island's bar, quitting the app or locking the screen.
- **How it works.** The tools are `screenshot` (the allowed apps' windows, through ScreenCaptureKit), `click`, `double_click`, `type`, `key`, `scroll`, `wait`. Coordinates are in the screenshot's space and NotchMeow maps them to the screen. Events are posted with CGEvent; the focused element is read with the Accessibility API only to refuse secure fields. After each action NotchMeow takes a fresh screenshot and returns it to the brain.
- **Brains.** Any brain with `tools` and `vision`: Claude plan (MCP image results; builder to verify Claude Code passes them through), Anthropic and OpenAI by native tool use (their own computer-use tool types may be used later for accuracy, call 12), local models that report both. A local model that reports `vision` and `tools` is allowed with a note that small models are unreliable at this.
- **Privacy.** Screenshots exist only in memory for the length of the run and are never written to disk or the log. They go to the chosen brain and nowhere else; the start card says which. On a local brain they stay on the Mac.

## Privacy and CPU

- **Where things are.** Memory: `~/Library/Application Support/NotchMeow/companion/memory.md`. Conversations: `.../companion/conversations/<id>.json`. Both are plain files with owner-only permissions (0600), in the app's container on the App Store build. No Keychain item holds any of it; the Keychain keeps API keys only (E1), as today. The user can open, edit, export (copy) and delete them from the app; deleting from the app deletes the file.
- **What the companion may store in memory:** short notes the user wrote or approved by not undoing, about himself, his preferences, his project names and what he said he is working on. Never a secret-shaped string, a full path, a prompt copied from an agent, an assistant reply of an agent, file contents, a screenshot or a tool result (rule 3).
- **What leaves the Mac:** the conversation, the memory (if on), the "Right now" block (if on), the tool results the brain asked for, and, in a computer-use run, the screenshots of the allowed windows: to the one brain the user picked, and every reply is labelled local, network or cloud as in E1. The Memory screen and the start card say it in the same words. "What the AI saw last": Settings → AI and chat → Companion has a viewer of the last request's text parts (not images), kept in memory only and gone at quit, so the user can check what was sent (this is the "what was sent" log E1 deferred).
- **No telemetry.** No analytics, crash reports or counters of NotchMeow's own. `nm.log` records event types and error kinds, never content (E1's rule).
- **Fallbacks.** Auto's cloud to local fallback (E1) stays; the reverse never happens. A fallback to a brain without tools drops the tools for that reply and says so.
- **0 % CPU hidden.** The chat does nothing without a user message. No polling, no timer that runs hidden, no music observer added, no MCP endpoint or computer-use code alive between turns. The recap uses the island's open event and the existing presence signal. The pop-out window, if open, is a normal window with no work of its own while idle.
- **Claude plan.** E3's rules hold: no keys or tokens in its environment, no reading of Claude Code's credentials, unmodified `claude` only, "Use my Claude plan" as the label, the legal re-check in the release checklist. The MCP endpoint is NotchMeow's own and adds nothing that reads Claude Code's files.

### What the research found (sources; "unverified" marks what the builder must prove against the installed CLI)

**Codex CLI (OpenAI).**
- Non-interactive: `codex exec "<task>"`; progress goes to stderr, the final message to stdout. `--json` turns stdout into JSON Lines with the events `thread.started`, `turn.started`, `turn.completed` (carries `usage`), `turn.failed`, `item.started`/`item.completed` and `error`; item types include agent messages, reasoning, command executions, file changes, MCP tool calls, web searches and plan updates. Source: https://learn.chatgpt.com/docs/non-interactive-mode (moved from developers.openai.com/codex/noninteractive). The exact field names of an agent-message item are not on that page: unverified; the fake `codex` is built from a real recorded run.
- Flags: `--sandbox read-only|workspace-write|danger-full-access` (`read-only` is the default for `exec`), `--model`/`-m`, `--ephemeral` (no session files written), `--skip-git-repo-check`, `--cd`/`-C`, `-o`/`--output-last-message <file>`, `--output-schema <file>`, `--ignore-user-config`, `--ignore-rules`, `exec resume --last|<id>`. Sources: the non-interactive page above and https://learn.chatgpt.com/docs/developer-commands?surface=cli. `--full-auto` is gone (same page).
- Sign-in state: `codex login status` "prints the active authentication mode and exits with 0 when logged in" (developer-commands page). The output text and the exit code when logged out are not documented: unverified. By default `codex exec` reuses the saved CLI login; the page also warns that ChatGPT-managed auth lives in `~/.codex/auth.json` and "should be treated like a password" (non-interactive page). NotchMeow therefore never opens that file; it only runs `codex login status` and reads the exit code.
- Platforms: the CLI has Windows (with a Windows sandbox and WSL page), Linux and macOS support (developer-commands page, partial; unverified for native Windows `exec`).
- Differences from Claude Code: no per-tool allow list on the command line (the control is the sandbox and approval policy); a read-only sandbox still lets the agent read files in its working directory; the MCP servers come from the user's `config.toml` unless `--ignore-user-config` is passed.

**Gemini CLI (Google).**
- Non-interactive: `gemini -p "<prompt>"` (headless also starts when stdin is not a terminal). `--output-format text|json|stream-json`. `json` is one object (`response`, `stats`, optional `error` with `type`, `message`, `code`). `stream-json` is JSONL with the events `init` (session id, model), `message` (user and assistant chunks), `tool_use`, `tool_result`, `error` (non-fatal) and `result` (final, with stats). Exit codes: 0 success, 1 general or API error, 42 input error, 53 turn limit. Sources: https://geminicli.com/docs/cli/headless/ and https://google-gemini.github.io/gemini-cli/docs/cli/headless.html. The field names of `message` (role, content, delta) are not documented: unverified.
- Flags: `--approval-mode default|auto_edit|yolo|plan` (`plan` is the only read-only mode), `--model`/`-m` (aliases `auto`, `pro`, `flash`, `flash-lite`, or a model name), `--sandbox`/`-s`, `--yolo` (deprecated), `--allowed-tools` (deprecated for the Policy Engine). Source: https://raw.githubusercontent.com/google-gemini/gemini-cli/main/docs/cli/cli-reference.md.
- Sign-in state: no status command is documented. Headless mode "will use your existing authentication method, if an existing authentication credential is cached"; without one it needs an environment variable (`GEMINI_API_KEY`, Vertex AI). Source: https://geminicli.com/docs/get-started/authentication. A third-party report shows the message "Please set an Auth method in your settings.json or specify one of the following environment variables" when none is set (https://geminicli.com/docs/get-started/authentication.md; unverified wording). So the state can only be known by running a turn or a one-word probe.
- **Material risk (changes the plan): on 18 June 2026 Gemini CLI stopped serving Google AI Pro, Google AI Ultra and the free individual tier.** It stays for Gemini Code Assist Standard/Enterprise organisations and for paid Gemini API keys; individuals are moved to **Antigravity CLI** (built in Go, not at feature parity at launch, closed source per press reports). Sources: https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/ and https://geminicli.com/docs/cli/headless/ (banner). Antigravity CLI is said to have a headless login flow and an API-key mode, but its non-interactive flags and output events are **not documented in anything fetched**: unverified (migration docs are at antigravity.google/docs/gcli-migration). A "Google plan" brain for an individual with a Google account is therefore a bet on Antigravity CLI, not on Gemini CLI.
- Platforms: Node-based Gemini CLI runs on macOS, Windows and Linux (unverified here; Antigravity CLI's platforms unverified).

### What the research found (sources; "unverified" must be proven by the builder against the installed `opencode`)

- **Two non-interactive routes exist.** `opencode run [message..]` takes `--format json` (raw JSON events), `--model provider/model`, `--session`, `--continue`, `--agent`, `--dir`, `--file`, `--auto` (auto-approves permissions not explicitly denied) and `--attach <url>` to a running server. https://opencode.ai/docs/cli/ And `opencode serve` runs a headless HTTP server: default `127.0.0.1:4096`, optional HTTP basic auth through `OPENCODE_SERVER_PASSWORD` (user `opencode`), an OpenAPI 3.1 spec at `/doc`. https://opencode.ai/docs/server/
- **The server API covers a whole chat turn:** `POST /session` to create, `POST /session/:id/prompt_async` to send (204, no wait), `GET /event` (server-sent events, first event `server.connected`) to follow the turn, `POST /session/:id/abort`, and `POST /session/:id/permissions/:permissionID` with `{ response, remember? }` to answer a permission. https://opencode.ai/docs/server/ The SDK documents `config.providers()` ("list providers and default models") but not whether it lists only connected providers, and its event types are not listed in the prose. https://opencode.ai/docs/sdk/ **Unverified: the event names and fields of a streamed turn, and the permission event shape. Read them from `/doc` and from recorded runs.**
- **Permissions:** rules `allow` / `ask` / `deny` per tool; on `ask` the answer is `once`, `always` or `reject`; `read` allowed (`.env` denied), `edit`, `bash`, `webfetch` and others configurable, most default to `allow`. https://opencode.ai/docs/permissions/ A chat that must be Read-only therefore cannot rely on defaults: the permission set is passed explicitly (see the levels table; the `OPENCODE_PERMISSION` and `OPENCODE_CONFIG_CONTENT` environment variables carry inline JSON, documented at https://opencode.ai/docs/cli/, **unverified that inline config overrides the user's own `opencode.json` rather than merging**).
- **Sign-in state.** Credentials are stored in `~/.local/share/opencode/auth.json` and `opencode auth list` shows what is configured. https://opencode.ai/docs/providers/ NotchMeow never opens that file. What it may use instead: the exit status and text of `opencode auth list` (names of connected providers, no secrets; **unverified that its output never prints a key or token**; if it does, the row uses "Not found / Ready" from `opencode --version` plus the last turn's result only), and `GET /config/providers` or `GET /provider` on a server NotchMeow itself started (**unverified which one lists only connected providers**).
- **License and platforms:** MIT; macOS, Windows, Linux. https://github.com/sst/opencode
- **Terms of the providers behind it (not legal advice).** OpenCode can connect other providers' subscriptions. For Anthropic: OpenCode's own docs say "Anthropic explicitly prohibits" using Claude Pro/Max in OpenCode through plugins and that it stopped bundling such plugins in 1.3.0 (https://opencode.ai/docs/providers/). ### How it runs: NotchMeow's own `opencode serve` (recommended)

NotchMeow starts and stops **its own** `opencode serve` for the chat, on `127.0.0.1` and a random free port, with a random one-time password in `OPENCODE_SERVER_PASSWORD` that lives in memory and dies with the process. It is not the user's server and not the pill's plugin. Reasons: a chat turn needs the permission round trip, the stream and an abort, which the server API gives and `opencode run --format json` does not (a `run` cannot hand a permission to the client; its `--auto` approves instead, which breaks "nothing is approved without a click"); and a server NotchMeow owns means no port left open and no credential kept after quit. `opencode run` stays the simple fallback for Chat only and Read-only if the spike finds the server awkward on Windows.

Process rules (the same as E3's for `claude`): the user's installed `opencode` is run unmodified; the binary is found by a locator (PATH, Homebrew, npm, Scoop, Chocolatey locations) and never downloaded; the server starts on first use of the brain, is reused between turns, and stops after a quiet period and at app quit (no polling: one idle one-shot timer); stdout and stderr are not logged; `nm.log` holds the command's exit status and OpenCode's version only.

### The three levels

| Level | How it is enforced | Folder |
|---|---|---|
| Chat only | A session in an empty NotchMeow temp folder with every permission set to `deny` (web fetch and search allowed only where the Claude plan's Chat only allows them, the same rule as call 10) | empty temp |
| Read-only | The chosen folder, permissions `read`, `glob`, `grep` allow; `edit`, `bash`, `webfetch`, `task`, `external_directory` all `deny` | chosen |
| Agent | The chosen folder; reads allow, `edit`, `bash` and the rest set to `ask`; every `permission.asked` event becomes NotchMeow's approval card in the chat; **Allow once** → `once`, **Deny** → `reject`; no "Always" and never `--auto` | chosen |

The permission set is sent with the session and the process environment, never by editing the user's `opencode.json`. A fake that tries to write in Read-only and Chat only must see it refused. **Unverified (the spike must prove, and the plan is not final until it does): that the passed permission set wins over the user's own config and over a project's `.opencode` folder, that a plugin the user installed globally cannot grant what the level denies, and that `doom_loop` and `external_directory` still ask or deny.** If the user's own plugins or rules can loosen a level, the chat says so in a plain line at Agent and refuses Read-only and Chat only, the way E3 describes Claude Code's own config (and is told to the owner).
