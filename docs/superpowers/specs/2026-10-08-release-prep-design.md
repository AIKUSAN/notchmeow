# Sub-project D, stage 1: tester builds and the site

**Status:** design approved in chat on 2026-10-08, section by section. This is the written spec for review.
**Parent spec:** `docs/superpowers/specs/2026-10-03-notchmeow-design.md` (sub-project D: "Public release: Developer ID signing and notarization, Windows signing, docs site"). **Builds on:** everything merged on `notchmeow/rebrand` at `762cdc3`, which includes sub-projects A and B on both apps and the sound pack (C, stage 2). This document covers D's first stage only. Signing, which costs money, is stage 2 and gets its own short design when the owner is ready to buy the accounts.

## Goal
Get NotchMeow into the hands of a few chosen testers on macOS, Windows and Linux, and give it a portfolio-quality page, without paying for signing yet. Every build a tester receives has first been checked on the owner's own machines: the Mac by a QA session and then by the owner, Windows by the owner on their Windows laptop. Nothing is published as a GitHub release in this stage. The eventual public release on the owner's GitHub (1.0.0, signed) is stage 2.

## 1. One version number everywhere
- **`scripts/set-version.sh <version>`** writes one version into every field that carries it:
  - `NotchBuddy/project.yml`, the main app's `CFBundleShortVersionString`, and its `CFBundleVersion` (the build number) raised by one;
  - `NotchBuddy/Resources/Info.plist`, regenerated by `xcodegen` and committed, as `release.sh` already expects;
  - `windows/package.json` and the two top-level `version` fields of `windows/package-lock.json`;
  - `windows/src-tauri/tauri.conf.json`;
  - `windows/Cargo.toml` (`[workspace.package] version`) and the `notchmeow` and `notchmeow-hook` entries of `windows/Cargo.lock`.

  It changes nothing else. The App Store variant (`io.github.aikusan.notchmeow.store`) keeps its own `1.0`, because the App Store is not part of D.
- **`scripts/check-versions.sh`** prints every field and fails when any two differ. `release.sh` runs it in both modes, and the Windows and Linux workflows run it on tags and on manual runs. It does not run on every push, because the inherited versions disagree (0.1.4 and 0.1.1) until the first `set-version.sh`.
- A version is three whole numbers (`0.9.0`), because macOS reads `CFBundleShortVersionString` that way.
- **`CHANGELOG.md`** gets a `## 0.9.0 — tester build` section, made from the "Unreleased (NotchMeow)" list at the cut. Coucou's sections stay below as history.
- **No tags for tester builds.** Each build records its branch and commit instead (section 2). The `v1.0.0` tag belongs to stage 2.

## 2. The Mac tester build
- **`scripts/release.sh <version> --tester`** is a third mode next to the existing signed release and `--finish`:
  - It runs the same checks as today: no uncommitted change to tracked files, a `## <version>` section in `CHANGELOG.md`, and the Info.plist version. It also runs `check-versions.sh`.
  - It works from any branch, not only `main`, and records the branch and the commit.
  - It runs `xcodegen`, then a Release build signed ad hoc (`CODE_SIGN_IDENTITY=-`), which keeps the hardened runtime and the entitlements.
  - It checks the result: `scripts/check-app-binary.sh <app> release` passes (no debug panel), `lipo` shows Apple silicon and Intel, and `codesign --verify` passes.
  - It writes three files to `/tmp/notchmeow-release-<version>/`: `NotchMeow-<version>-mac.zip` (made with `ditto`), its `.sha256`, and a short `NOTES.txt` holding the version, branch, commit, date, three install lines and the testers page's address.
  - It does **not** notarize, tag, push or create a GitHub release.
- The existing signed mode is left as it is, for stage 2.
- **Installing on a tester's Mac (macOS 15 or later):**
  1. Unzip and drag NotchMeow to Applications, then open it. macOS refuses it once, because it isn't notarized.
  2. Go to System Settings → Privacy & Security → **Open Anyway**, and confirm.
  3. **Updating** to a later tester build: replace the app. macOS then asks once whether the new build may read NotchMeow's saved keys, because an unsigned build's identity changes with every build. Answer **Always Allow**.
- **The permission prompts in English.** Today's three strings are inherited in French ("Pour sauter au terminal…"). They become English, in both builds where they appear:
  - `NSAppleEventsUsageDescription`: "NotchMeow uses this to jump to your terminal, send mail and control Music."
  - `NSAccessibilityUsageDescription`: "NotchMeow uses this to read the active window's title and attach it as context."
  - `NSLocalNetworkUsageDescription`: "NotchMeow uses this to reach an AI model server you added on your network."

## 3. Windows and Linux tester builds
- After the Mac checks pass (section 6), the owner merges to `main`, pushes, and runs the **Windows** and **Linux** workflows by hand (GitHub → Actions → Run workflow) on `main`.
- Publishing stays off (`PUBLISH: 'false'`). Nothing becomes a release, and the files stay in the run for 3 days (the workflows' `retention-days`). While they last, the repository being public means any signed-in GitHub user could download them.
- **The only workflow change:** `check-versions.sh` also runs on manual runs. Today the version check runs only on tags.
- **Windows:**
  - Testers get the **portable pair**: `notchmeow.exe` and `notchmeow-hook.exe` side by side. It runs without an installer, and the Claude Code hooks work, because `hooks.rs` looks for the hook next to the app.
  - The unsigned NSIS installer stays unused until signing, because Defender flags it as a trojan (a false positive).
  - SmartScreen says "Windows protected your PC": **More info → Run anyway**.
  - The owner downloads the pair from the run and sends it to their Windows laptop with LocalSend. Downloading needs a GitHub sign-in, so the owner does it, or asks the main session to (it asks first, naming the file and its size).
- **Linux:**
  - The run makes the AppImage, the `.deb`, the `.rpm` and `SHA256SUMS`.
  - Before the push, the main session also tries building the `.deb` and `.rpm` in the existing `notchmeow-linux-dev` image, as a build check. It never builds or pulls an image and downloads nothing. If bundling needs a download, the GitHub run alone makes them.
  - Install: the AppImage needs `chmod +x` and then runs; `sudo apt install ./NotchMeow-….deb`; `sudo dnf install ./NotchMeow-….rpm`.
  - On GNOME the island is a plain always-on-top window, as the README already says.

## 4. Tester notes and feedback
- **`docs/testers.html`, "Try a tester build":** a public page on the site, linked from the home page's Get it section. It holds:
  - **Install** for each platform (sections 2 and 3), and **uninstall**: remove the Claude Code hooks in Settings first, then delete the app.
  - **What to try:**
    - install the Claude Code hooks from Settings (NotchMeow backs up `~/.claude/settings.json` and shows the diff first);
    - run a Claude Code session and approve a permission from the notch;
    - answer a question;
    - drop a file on the notch;
    - pick a coat, a motion style, a personality and a display mode;
    - start a subagent to see its kitten;
    - leave it idle ten minutes to see the cat sleep;
    - on the Mac, play music to see it dance.
  - **What to tell the owner:** the computer and system version, NotchMeow's version, what was tried, what happened, and a screenshot.
- The Mac zip's `NOTES.txt` carries the short version and the page's address.
- Nothing is collected. There is no feedback button and no telemetry: testers message the owner however they already talk.

## 5. The site
- **GitHub Pages from `docs/` on `main`.** The owner switches Pages on in the repository's settings after the push. Address: `https://aikusan.github.io/notchmeow/`.
- **Two pages,** `index.html` and `testers.html`, sharing `site.css`. The colours come from the theme pipeline (`shared/theme.json` covers "the fork's own pages"). The existing placeholder `index.html` and `site.css` are replaced.
- **The home page:**
  - **Live Shrimpy and Momo at the top.** They blink, follow the visitor's cursor, and react to a click with a happy emote. A row of the 16 coats lets the visitor try them.
  - **What it does,** with pictures: the island with agent sessions, an approval from the notch, subagent kittens, the three display modes and the coats sheet.
  - **Private by design:** no telemetry, no account, keys in the system keychain.
  - **Get it:** "Tester builds by invitation" (a link to the testers page), the public release "coming", and build from source (a link to the README).
  - **Credits:**
    - Coucou by Louis Raillé (MIT), with the independence line from the README;
    - the sound credits (`docs/SOUND-CREDITS.md`);
    - NotchMeow's own assets (`LICENSE-ASSETS.md`).
- **The live cats reuse the Windows app's engine and renderer** (`windows/src/cat/`), which are already tested against the shared fixtures. So the page's cats are the app's cats, not a third copy.
  - The Vite already in `windows/` bundles them into fixed file names under `docs/assets/`, together with the generated theme CSS. The output is committed, because Pages serves files as they are.
  - **`scripts/check-site.sh`** rebuilds the bundle into a temporary folder and fails when the committed one differs. It also fails on any request to another host: no script, style, font or image from outside `docs/`. Links to GitHub and to the credits are allowed. The Windows tests workflow runs it, since it has `node_modules`.
- **Pictures** come from the render scripts, with no app launch:
  - `render-cats.sh` with `--island`, `--kittens` and the coats sheet;
  - `render-cat-settings.sh --mode …` for the display modes;
  - `render-plan-card.sh`.

  A feature without a render script (the approval card) gets a small one in the same style. `scripts/render-site.sh` redraws them all into `docs/assets/img/` at 2×, and is run at each tester round's cut.
- **Behaviour:**
  - With reduced motion turned on, the cats hold a still frame.
  - The cats stop drawing when the tab is hidden or scrolled out of view.
  - The page works on a phone.
  - Every picture has alt text.
  - No cookies, no analytics, no outside fonts.
- **The README:** "There are no releases yet" becomes "Tester builds (0.9.x) are by invitation; the public release is coming", with a link to the site. Roadmap row D says stage 1 is in progress.

## 6. Checking a build before testers get it

### The Mac QA session
- A separate worktree chat session on Haiku 5.5 at high effort (CLAUDE.md's model rule of 2026-10-12), with its own short brief, run after each Mac tester build and before the owner's check.
- **The owner lifted the rule "never launch NotchMeow" for this session only, on 2026-10-08.** Every other session keeps the rule.
- **What it does:**
  - **Hooks first:** before anything else, it checks that no NotchMeow hooks are installed in `~/.claude/settings.json`. That is true today; if hooks are installed, it stops and reports.
  - **Install:** it moves any NotchMeow in `/Applications` to the Trash (none is installed today), unzips the tester build into `/Applications`, and opens it.
  - **Scripted events only:** it drives the app with scripted hook events sent straight to the running build: `scripts/fake-subagent-events.py`, and sample payloads piped into the `nm-hook` relay the way Claude Code pipes them. It never installs hooks and never writes to `~/.claude`.
  - **What it checks:**
    - the greeting;
    - sessions in the island;
    - an approval and a question, which it answers;
    - kittens arriving and leaving;
    - the three display modes;
    - a coat change;
    - Settings → Cat;
    - the ten-minute sleep (on a shortened timer only if the build offers one; otherwise skipped);
    - idle CPU with the island hidden, which should round to 0 %.
  - **Report:** it takes screenshots with screen control (the owner approves its access to NotchMeow and System Settings), and reports the screenshots, the CPU readings and anything wrong.
  - **It never touches real permissions:** it clicks Allow, Deny or an answer only on requests it sent itself, which are marked in their payload, and never on one from a real agent.
  - It leaves the tester build installed for the owner's check, and quits it at the end.
- The QA session cannot judge sounds or feel. The owner's own check of the same zip comes next and is the last word.

### The owner's checks
- **Mac:** the same zip, installed as a tester would, including the "Open Anyway" step and installing the real hooks through Settings.
- **Windows:** the portable pair on the owner's Windows laptop, after the push.
- Anything found is fixed on `notchmeow/rebrand` and a new tester build is cut.

## 7. Build order

**Two plans, run in parallel worktree sessions** (Haiku 5.5 at high effort under CLAUDE.md's model rule of 2026-10-12, each with its own branch):
1. **D1-tools:**
   - `set-version.sh` and `check-versions.sh`, with tests on temporary copies of the version files;
   - `release.sh --tester` and `NOTES.txt`;
   - the English permission prompts;
   - `check-versions.sh` in the Windows and Linux workflows' manual runs;
   - the Mac QA session's brief, as a document under `docs/`.

   Its verification runs in a throwaway clone, because the inherited versions disagree until the cut. There it runs `set-version.sh 0.9.0`, then `release.sh 0.9.0 --tester` on a scratch commit, and checks the zip without launching it.
2. **D1-site:**
   - the site bundle and `check-site.sh`;
   - `index.html`, `testers.html` and `site.css`;
   - `render-site.sh` and the missing render script;
   - the README lines.

   An owner checkpoint shows the page, from a local static server in a headless browser, before it is committed.

**Then the 0.9.0 round,** a checklist the main session follows, not a plan:
1. The small fixes after B have merged, and so have D1-tools and D1-site.
2. `set-version.sh 0.9.0`, the `## 0.9.0 — tester build` section and `render-site.sh`, in one commit (with the owner's OK).
3. `release.sh 0.9.0 --tester` on the owner's Mac.
4. The Mac QA session runs. The main session reviews its report and screenshots.
5. The owner checks the same zip. Anything found is fixed, and the round goes back to step 3.
6. The Linux `.deb` and `.rpm` build check in Docker.
7. **The owner** merges `notchmeow/rebrand` into `main`, pushes, and switches Pages on.
8. **The owner** runs the Windows workflow and checks the portable pair on their laptop.
9. **The owner** runs the Linux workflow.
10. The owner hands the files out, with the testers page's address.

## Out of scope
- **Signing and notarization:** Apple's Developer Program and a Windows certificate. That is stage 2, with its own short design. `release.sh`'s signed mode stays ready for it.
- **The Mac App Store** submission (the `.store` variant keeps building and passing its checks).
- **An auto-updater:** testers replace the app by hand. Any later update check would be opt-in, because the app calls only services the user configured.
- **Telemetry, crash reporting and analytics**, on the site too.
- **Homebrew and winget.**
- **The desktop cat,** which joins a later tester round.

## Risks
- **Gatekeeper's wording and steps change between macOS versions.** The testers page names macOS 15's steps and shows the System Settings route, which has stayed stable.
- **Windows Defender may flag the portable exe as well.** Then Windows waits for signing, and the testers page says so.
- **Keychain prompts on every tester update** (unsigned identity) may confuse. The page and `NOTES.txt` warn about them.
- **A public repository:** pushing makes the code public (it already is a public fork), and the run's files can be downloaded by signed-in users for 3 days.
- **Vite output drift:** a dependency update could change the bundle's bytes. `check-site.sh` catches it, and the fix is to rebuild and commit.

## Done means
- `set-version.sh 0.9.0` followed by `check-versions.sh` agrees on every field, and the tests pin the files and lines it touches.
- `release.sh 0.9.0 --tester` produces the zip, checksum and notes, with a universal, ad-hoc signed app that passes `check-app-binary.sh release`, and publishes nothing.
- The Mac prompts are in English in both builds.
- The site passes `check-site.sh`: its bundle is current and it makes no outside request. It shows live cats, the feature pictures, the testers page and the credits, and works with reduced motion and on a phone.
- The 0.9.0 round's checklist has been followed: the Mac QA session's report and the owner's own checks passed before any file reached a tester.
