# The link contract

Sub-project G2 (`docs/superpowers/specs/2026-10-04-file-shelf-transfer-design.md`, "G2. Between your machines" and "G1-0 and G2-0") moves files between a Mac and a Windows/Linux PC that both run NotchMeow, over the local network. The macOS app (Swift, on CryptoKit and `Network.framework`) and the Windows/Linux app (Rust, on the `snow` and `mdns-sd` crates, with TypeScript for the cards) each implement the same rules natively. Everything they must agree on to talk to each other is written once, here and in `tests/fixtures/link/`, and each app tests itself against the fixtures. The cross-app test of G2 (the Swift and the Rust code pair over loopback and send files both ways) comes on top of this contract and does not replace it.

**`tests/fixtures/link/reference.py` is the tie-breaker.** It is a Python program (standard library only) with every rule written as plainly as possible, including the X25519, ChaCha20 and Poly1305 that the Noise handshakes need (checked against the RFC 7748 and RFC 8439 test vectors). The JSON files are written by `build_cases.py`, with every expected answer typed out by hand (the Noise vectors and the pairing codes are pasted once from the reference and then frozen), so the fixtures and the reference check each other. If an app and a fixture disagree, the app is wrong. The reference is not constant-time and no app may use it.

The look of the cards, the discovery itself, the sockets, the Keychain items, the streaming of a file to disk and the quarantine attribute are not tested here. This contract is the bytes on the wire, the rules for what to accept, and the arithmetic that both ends must agree on.

## Run it

```
bash scripts/test-link-contract.sh                        # the reference against every fixture, then the no-drift check, then a node parse of every fixture
python3 -B tests/fixtures/link/build_cases.py             # rewrite the JSON files after an intended change
python3 -B tests/fixtures/link/build_cases.py --check
```

Python 3.9 or newer, nothing to install; it takes a few seconds. CI runs the script next to the other contracts. Both app plans add their own replay of the files: G2-mac and G2-tauri.

## On the wire

One TCP connection carries one conversation, pairing or transfer. Numbers are big-endian. Everything is a **record**: a `u16` length (1 to 65535, so 0 is an error and closes the connection) and that many bytes. A record holds one of: the preamble, one Noise handshake message, or one Noise transport message. `split_records` cuts a stream into whole records and keeps the rest.

1. **The preamble** is the first record, from the initiator, in the clear: 18 bytes, `version` (1), `mode` (1 pair, 2 transfer) and the sender's 16-byte `device id`. When pairing the id is 16 zero bytes (the machines do not know each other yet); in a transfer it must not be zero, and the responder uses it to find the stored key of that peer, because `KK` needs the initiator's static key before the first message. An id it does not know closes the connection.
2. **The handshake**, one record per Noise message: `Noise_XX_25519_ChaChaPoly_SHA256` (3 messages) for a pairing, `Noise_KK_25519_ChaChaPoly_SHA256` (2 messages) for a transfer, both with the **prologue** `notchmeow-link/1` (ASCII), so that two versions of the protocol cannot complete a handshake. The ephemeral keys are random; only the fixtures inject them. A DH result of 32 zero bytes (a low-order point) aborts. Nothing is sent after a failed handshake: the connection is closed.
3. **Pairing** runs in a fixed order, inside the `XX` handshake (details in "The pairing code" below). The payload of message 1 (in the clear, as `XX` has no key yet) is the initiator's **commitment**, 32 bytes. The payload of message 2 is the responder's **hello**, and of message 3 the initiator's hello, which **reveals** its nonce. A hello is `version` (1), the sender's 16-byte device id (not all zero), a 32-byte `nonce`, `name length` (`u8`) and the device name (1 to 63 bytes of strict UTF-8 with no control, format, surrogate, line-separator or paragraph-separator character, no character of the invisible table (every Default_Ignorable code point and U+2800, the same table as the file-name rule below: refused as `name-chars`), and no space at either end). It is encrypted, so the name on the "Pair with <name>?" card is the authenticated one; the name in the advert is not trusted. The device id in a hello is checked against the machine's own id and its paired devices (the device-id rule below): a hello with no valid device id is refused as `reveal-length` or `nonce-length`, and one with the all-zero id as `device-id`, whatever the machine knows; a hello whose id is this machine's own is refused as `own-id`, and a hello whose id is paired under another key is refused as `id-key-mismatch`. The responder shows the code once it has checked the reveal (`pair_responder_step`, event `reveal`). The initiator shows the code once it has the responder's nonce and has sent its own reveal (`pair_initiator_step`, event `nonce`). Then the user answers, and a `pair-yes` or `pair-no` tells the other side; a key is stored only when both said yes. After the handshake a pairing connection carries only `pair-yes` and `pair-no`, and a port must refuse any other frame on a pairing connection (the reference's pairing machines take events, not frames, so the reference does not check this yet).
4. **Transfer**: after the `KK` handshake each Noise transport message holds one **frame**: a type byte, the 16-byte transfer id, then the body. The payloads of the `KK` handshake are sent empty by both sides, and a port must refuse a non-empty one (the reference does not enforce this yet, so it is a port requirement).

| Frame | Type | Body |
|---|---|---|
| `offer` | 1 | `size` (`u64`), `name length` (`u16`, 1 to 1020), the name (strict UTF-8, as the sender has it), `kind length` (`u8`, 0 to 127), `kind` (printable ASCII, the file's type, advisory: never used to decide anything) |
| `accept` | 2 | nothing |
| `decline` | 3 | `reason` (`u8`): 0 the user said no, 1 nobody answered in 2 minutes, 2 busy: this machine already has a transfer running (one at a time for the whole machine, whichever peer it is from; see "What each side does with each frame"), 3 too large, 4 the offer was not acceptable |
| `chunk` | 4 | `offset` (`u64`), then 1 to 65494 bytes of data |
| `done` | 5 | nothing |
| `cancel` | 6 | nothing |
| `pair-yes` | 33 | nothing, and no transfer id: the type byte alone. After a pairing, "They match" was clicked |
| `pair-no` | 34 | nothing, the type byte alone. The other side's user said the codes differ |

A frame may not have a byte left over (the `pair-yes` and `pair-no` frames travel in the transport messages that follow the pairing handshake and are one byte each), and a decoder must be strict: UTF-8 without surrogates, overlong forms or code points over U+10FFFF (a decoder that repairs bad bytes is wrong), and ASCII for `kind`. The limits are `chunkMax` 65494 (so that a chunk frame and the 16-byte tag fill a Noise message of 65535 bytes exactly), `rawNameMax` 1020 (255 code points of up to 4 bytes) and 4 GiB per transfer. A sender cuts a file into chunks of `chunkSize` 32768 bytes (`plan_chunks`) and accepts any chunk up to `chunkMax`.

The advert (`_notchmeow._tcp`) carries a TXT record with `v` (the text `1`), `id` (32 lower-case hex digits, not all zero) and `name` (as a device name). `parse_txt` accepts or rejects it, because anyone on the network can send one. It gives a machine something to show in a list and nothing more: only a paired key gets a session. `parse_txt(txt, own_id)` refuses an advert only when its `id` is this machine's own id (`own-id`) or the all-zero id (`device-id`, as in the hello), or when `own_id` is given but is not canonical, a null one included (`device-id`, fail closed). A port omits `own_id` when it has no id yet and never passes null. The advert carries no key, so it cannot decide a key mismatch: a paired id under another key is refused at the hello, once the key is known.

## The pairing code

The six-digit code must not be something a man in the middle can aim at. A code made from the handshake alone can be: the attacker, sitting between two machines, runs one handshake with each, and grinds its own keys offline until the two codes agree, about 10^6 tries for 6 digits. So the code is made with a **commit-then-reveal** step, the short-authenticated-string pattern of Vaudenay ("Secure Communications over Insecure Channels Based on Short Authenticated Strings", CRYPTO 2005), of ZRTP's hash commitment (RFC 6189) and of Bluetooth's numeric comparison (Core Specification, Vol 3, Part H, 2.3.5.6.2, with `f4` and `g2`). The owner chose it over a longer code on 2026-10-14.

1. The initiator draws a fresh 32-byte nonce `nI` and sends `commit_of(nI, sI)` = `SHA-256("notchmeow-link pairing commit v1" + sI + nI)` as the payload of message 1, where `sI` is its static public key. The commitment hides `nI` and binds `sI`.
2. The responder, which has seen only the commitment, answers with its nonce `nR` in its hello (message 2).
3. The initiator reveals `nI` in its hello (message 3). The responder opens message 3, which also shows it `sI`, and checks `commit_of(nI, sI)` against what it got first. A wrong nonce and a wrong key give the same refusal (`reveal-mismatch`) on purpose: the commitment cannot tell them apart and the attacker learns nothing from which it was.
4. Both compute `pairing_code(nI, nR, sI, sR)` = the first 8 bytes of `SHA-256("notchmeow-link pairing code v1" + sI + sR + nI + nR)` as a number, modulo 10^6, with leading zeros kept. Both users compare the two screens and answer.

**Why it holds.** Each of the attacker's choices towards each side (its static keys, its nonces) is made before the honest initiator's nonce is revealed, and the commitment stops the initiator, or an attacker playing the initiator, from choosing the nonce afterwards. So the code on each screen is a fresh unpredictable value to the attacker at the moment it commits to everything it can still vary, and it gets **one guess per pairing attempt**: about 1 in 10^6. An attempt is allowed once every 30 seconds, every failed one shows the users two different codes, and the window of 2 minutes covers the whole exchange. The static keys are in the code because the `XX` handshake authenticates them: a key substituted by a man in the middle gives a different code on the two screens.

**What is deliberately not in the code.** The handshake hash. The last sender's payload (its device name, free text) is in that hash and can still be varied after the sender has seen the other side's nonce, which would let the attacker grind the code offline again. The device name and id are not in the code either, for the same reason: the name on the card is whatever the other machine says it is, and the user decides by looking at the machine in front of them.

**The two machines.** `pair_responder_step` and `pair_initiator_step` run the order above one event at a time and are tested row by row. A refusal closes the connection and always has a cause (`because`): `commit-length`, `commit-replayed` (the same commitment seen again within the window: the responder keeps the recent ones across connections, `seen`), `attempt-too-soon`, `no-commit` (a reveal, or a nonce, with no commitment before it), `reveal-late`, `reveal-length`, `reveal-mismatch`, `device-id`, `own-id`, `id-key-mismatch`, `unexpected`, `start-length`, `nonce-repeated`, `nonce-length`, `window-closed` (an answer after 2 minutes) and `said-no`. An answer that is not exactly `yes` is a no. The machines also take the two device-id inputs of the device-id rule below, `own_id` (this machine's id) and `paired` (device id to the static key stored for it), both optional and kept from one step to the next; the responder's `reveal` event carries the initiator's device id as `peerId`, and the initiator's `nonce` event carries the responder's as `peerId`. Every machine refuses a hello with no valid device id (`reveal-length` or `nonce-length`) and one with the all-zero id (`device-id`), whether or not it knows either input, so a hello always has a usable id to check. The static key a hello is checked against is the remote static key that the Noise handshake authenticated, never a value in the hello, which carries none. A port must write `own_id`, the ids of `paired` and their keys in lower-case hex. A port omits `own_id` when it has no id yet and never passes null. A null `own_id` is present and is not an id, so it is not the unconfigured case: a machine whose `own_id` is null refuses every hello that has a valid device id as `device-id`, and an advert with a null `own_id` is refused as `device-id` (fail closed). A machine whose `own_id` is not 32 lower-case hex digits, or whose paired id is not 32 or whose paired key is not 64, refuses every hello that has a valid device id as `device-id` (fail closed: the value is never lower-cased to fit), and an advert with a non-canonical `own_id` is refused as `device-id`. The paired map is a snapshot in the machine's state, so a port must re-check it at the moment it stores a key (two pairings can overlap for up to 2 minutes, so a port that checked the map when its pairing started must check again before storing). The responder's refusal for `id-key-mismatch` looks the same on the wire as any other refusal of the hello: it sends nothing, raises no notice and closes the connection; the reason is only the local `because`. The initiator may already have shown its code before that refusal (it learns the responder's id from message 2, while the responder learns the initiator's id only at message 3), so a port clears the code when the connection closes, and no key is stored. The timing of that close is a documented limit, and it is a behaviour difference too: an unknown id leaves the connection open with a code on screen, while an id paired under another key closes at once, so a LAN peer that knows a device id can tell from the behaviour whether it is paired here under another key (the advert already exposes ids, so this adds little). The limit on probing is the 30 s gap between attempts.

The clocks, in whole milliseconds on a monotonic clock (an app counts an attempt when it starts a pairing and when it accepts an incoming one): one pairing attempt every 30 s (`pairing_attempt_allowed`: allowed at exactly 30 s), the pairing window closes after 2 minutes (`pairing_window_open`: open below 120 s), and an unanswered offer is declined after 2 minutes (`offer_expired`: expired at 120 s). A clock that went back or a value that is not whole milliseconds counts as "no" for the first two and "expired" for the third. The first frame of a transfer connection is a fourth clock: 10 s after its handshake (`LinkTransferReceive.firstFrameMs` = 10000 on the Mac), and it is out when that time has come (`first_frame_expired`: open at 9999 ms, closed at 10000 ms). A clock that went back, or a value that is not whole milliseconds, counts as "expired", as the offer does. The rule is in "What each side does with each frame".

## File names

`sanitize_name(raw)` gives `("ok", name)` or `("reject", reason)`. The name on the Accept card is the **sanitized** one, because it is the one that is saved.

**Whitespace collapses first** (answer 2b of the owner, 2026-10-14; file names only, the device names are unchanged). Before the checks, the code makes the NFC form and the NFKC form (the two the checks read), and in each one every run of these code points becomes one U+0020: U+0009 to U+000D (tab, line feed, vertical tab, form feed, carriage return), U+0020, U+0085 (NEL), U+00A0 (no-break space: whitespace here, by the owner's decision), U+1680, U+2000 to U+200A, U+2028 (line separator), U+2029 (paragraph separator), U+202F, U+205F and U+3000. The table is written out by hand (`NAME_SPACE_RUN` in `reference.py`), not taken from `unicodedata`. It runs before every check below, before the trim and before the byte cut, so the cut never splits a run, and a name made only of these code points is refused as `empty`. The consequence, asked for by the owner: a tab, a line break, U+0085, U+2028 and U+2029 in a file name are a space, and the name is accepted; before this rule they were refused as `invisible`.

**Rejected** (a real sender never sends these; the offer is declined as "not acceptable"): not text (`not-text`); a control, format or surrogate character (`invisible`: Unicode categories Cc, Cf, Cs, so NUL, the C0 and C1 controls other than the whitespace above, DEL, every bidi control, the zero-width space, joiner and non-joiner, the word joiner, the byte order mark, the soft hyphen and the tag characters), and every character of the table `INVISIBLE_RANGES` in `reference.py` (`invisible` too): every Default_Ignorable code point of Unicode (the list in DerivedCoreProperties.txt), that is U+00AD, U+034F, U+061C, U+115F-U+1160, U+17B4-U+17B5, U+180B-U+180F, U+200B-U+200F, U+202A-U+202E, U+2060-U+206F, U+3164, U+FE00-U+FE0F, U+FEFF, U+FFA0, U+FFF0-U+FFF8, U+1BCA0-U+1BCA3, U+1D173-U+1D17A and U+E0000-U+E0FFF, plus U+2800 (BRAILLE PATTERN BLANK, which is blank). The four Hangul fillers U+115F, U+1160, U+3164 and U+FFA0 (category Lo, but they show nothing) are among them. The table is written by hand and not taken from `unicodedata`, so the set does not change with the Python version; a `/` or a `\` (`separator`: so no path, no `..` part, no absolute path, no UNC path); nothing left once spaces and dots are trimmed (`empty`: `.`, `..`, `...`, spaces). The checks run on the NFC form and on the NFKC form, so full-width solidus, reverse solidus and dots are caught as what they fold to. The whitespace collapse runs first, then the checks in the order above.

**Rewritten** (platform differences, not attacks): `< > : " | ? *` become `_` (the colon also stops an NTFS alternate data stream); spaces at the start and spaces and dots at the end go; a Windows device name (`CON`, `PRN`, `AUX`, `NUL`, `COM0`-`COM9`, `LPT0`-`LPT9`, `COM` or `LPT` followed by U+00B9, U+00B2 or U+00B3 (answer 2c), `CONIN$`, `CONOUT$`: the part before the first dot, ASCII case-insensitive, also after NFKC) gets a `_` in front; a name over **200 UTF-8 bytes** is cut at a code point, keeping an extension of up to 16 bytes, and the spaces and dots the cut leaves at the end go; a name that starts with a dot gets a `_` in front so that it shows (`.txt` is saved as `_.txt`; the `_` is the first part, so no device name comes of it, and the cut runs again if the `_` makes the name too long). What is left once the cut and these rules are made must not be empty or dot-only, in NFC or NFKC: otherwise it is refused as `empty`, as an empty name is, so the byte cut never saves an empty name. The kept name is **NFC** (never NFKC: a ligature stays a ligature).

`unique_name(name, taken)` is `name (1).ext`, `name (2).ext` and so on, the smallest free number from 1, comparing in NFC and case-insensitively (the usual volumes of both systems do), giving up after 9999 (`None`: the transfer fails). Only the last extension of 16 bytes or less is kept apart (`a.tar.gz` becomes `a.tar (1).gz`), and a leading dot is not an extension (`.bashrc (1)`). A name from a Windows sender of 255 UTF-16 units can be 765 bytes of UTF-8; that is why the wire allows 1020 bytes and the saved name is cut to 200.

## What each side does with each frame

`receiver_step(state, event)` and `sender_step(state, event)` are pure: a state, one event (a frame, a click, a timeout), and the answer `{state, send, notify, abort}`. Tables in `flow-cases.json`; the rules in short:

- **Receiver.** An `offer` while idle: a size over 4 GiB is declined (3), a name the sanitizer rejects is declined (4), otherwise the card is shown and the state is `offered` (an empty file is allowed). An `offer` while something else is going on is declined as busy (2) and changes nothing. In the reference, busy is decided by each connection's own state (`receiver_step`, one connection). Across connections the app keeps one transfer place for the whole machine, and it declines an offer with reason 2 (busy) itself when the place is taken; the bullets below give the rule. **Only a click** (`accept`) starts the transfer; `decline` and a timeout answer with reasons 0 and 1. A `cancel` for the current transfer ends it; a `cancel` for any other id is ignored; a `cancel` with no transfer running is ignored. While an offer waits, the answer is Decline (a `cancel` click is ignored). A `cancel` the user clicks while receiving ends the transfer and sends a `cancel` frame.
- **Chunks.** The `offset` must equal the bytes received so far (a replayed or a skipped chunk is `order`), the sum may not pass the offered size (`overflow`), the id must be the transfer's (`id`). `done` is good only when the count equals the offer exactly (`short` otherwise). Any other frame in any other state is `unexpected`. Every abort closes the connection; nothing is saved as complete.
- **Sender.** `accept` or `decline` for its offer's id move it on; a frame for another id, or one that makes no sense in the state, closes the connection. A `cancel` with no transfer running is ignored, on the sender and on the receiver. A `cancel` during a transfer (offered or sending) ends it: the user's cancel sends a `cancel` frame, and a `cancel` frame from the receiver with the same id ends it without an answer. A `cancel` for another id during a sender's transfer closes the connection (the receiver ignores a `cancel` for an unknown id and does not close).
- The Noise layer already refuses tampered, replayed and reordered messages (the nonce is the message count); the checks above catch a peer that is paired but wrong or hostile.
- **One transfer for the whole machine.** An offer that arrives while its connection is idle asks the machine's one transfer place (`place_step`). It is granted only when no transfer of any peer holds the place and no card with buttons is on the island (a pairing code, a waiting offer, a transfer's Accept card). A refused offer is declined as busy (2) and changes nothing else, and the connection stays as it was. A second offer from the same peer is refused the same way while its transfer runs. The place is held from the grant until the transfer ends, and given back at once when the machine declines the offer itself (too large, a name it refuses). The Mac's `LinkBusy` (`claim`, `release`, `setCardLocked`) does this, and `LinkTransferReceive` asks it at the claim.
- **One decline per connection.** The machine's own declines are counted per connection: reasons 2 (busy), 3 (too large) and 4 (not acceptable), each sent in answer to an offer. The first one is sent. A second one on the same connection is not sent: for that offer nothing is sent and the connection is closed (the Mac's abort is "declines"). The user's no (0) and a timeout (1) are not counted, and an offer the machine accepts after a decline still gets its card. A sender therefore opens one connection per file (the Mac's send loop makes one `NWConnection` and one `LinkTransferSend` for each file). `receiver_connection_step`.
- **The first frame.** On a transfer connection the first frame is the offer: a pairing's hellos are handshake messages (messages 2 and 3), not frames. The receiver's clock starts at the end of the handshake, and while no offer is in hand (idle) the connection is closed when 10 s have passed. A frame that leaves the connection idle does not stop it: a refused offer (busy) or a cancel for a transfer the connection does not know. The clock stops only when an offer takes the connection on (offered: the offer's own 2 minutes, then the transfer's chunk clock of 60 s). A clock report that arrives in any other state is stale and does nothing. (The Mac's `LinkIdleWatch` in `LinkTransferReceive.run`, `firstFrameMs` = 10000.) Open at 9999 ms, closed at 10000 ms (`first_frame_expired`, `firstFrame[]`); `receiver_connection_step` with `{silent: true}`.

## Notes for ports

- **Noise.** Revision 34. `ChaChaPoly` is the 12-byte-nonce IETF ChaCha20-Poly1305 with a nonce of 32 zero bits and then the 64-bit message count, little-endian; not XChaCha. `SHA256` and the `HKDF` of the Noise spec (two outputs) are HMAC-SHA256. The starting hash is the protocol name itself: both names are 32 bytes long, so there is no padding (the reference pads a shorter name with zeros and hashes a longer one with SHA-256, as the Noise spec says). Reading a message whose tag fails must not move the counter. The reference refuses a DH output of all zeros; CryptoKit and `snow` may already do so, and a port must anyway.
- **JSON.** Integers are whole numbers; the fixtures hold no float. Hex fields are lower-case. A fixture that holds text with escapes (`\u202e`) is read by a strict JSON reader, as for the shelf.
- **Strings.** Byte limits (name 200, device name 63, wire name 1020) are UTF-8 bytes; the number of characters is not a limit. Compare names after NFC. The Unicode categories (Cc, Cf, Cs, Zl, Zp and Zs) come from the language's own tables, and those differ by Unicode version. The invisible set (`INVISIBLE_RANGES`) and the whitespace set (`NAME_SPACE_RUN`) are not taken from the tables: both are written out by hand in `reference.py`, the invisible set from the Default_Ignorable code points that the code's comment cites (DerivedCoreProperties.txt). The code names no Unicode version, so both sets must be re-checked when the Unicode version changes. The fixtures include U+FFF0, which is unassigned in some Unicode versions, and the table refuses it as `invisible` whatever its category, so a port must use the same tables and not the category alone.
- **Time.** The gaps use a monotonic clock, in whole milliseconds.
- **Secrets.** The static private key and the peers' keys live in the Keychain or Credential Manager and never in a log, a file or a fixture. The keys in the fixtures are plain byte patterns made for tests: never use one as a real key.
- **Not in this contract:** discovery and browsing, the sockets and their timeouts, the Keychain and Credential Manager items (`link.static-key`, `link.peer.<id>`), the cards, writing the file (the folder `Downloads/NotchMeow/`, quarantine, mark-of-the-web), the Send menu, and the Debug fake peer.

- The Noise vectors are generated by the reference with fixed keys and cross-checked with an independent implementation on CryptoKit; the published vectors can be added as more entries (`source`: `published`) without changing any code.
- The prologue is `notchmeow-link/1`; the preamble, the hello and the frame layouts above are this contract's own design.
- The pairing code comes from a commit-then-reveal step (the owner's decision), 6 digits only; the handshake hash is not an input and the reason is above.
- Chunks are cut at 32 KiB; 4 GB means 4 GiB inclusive (4294967296 bytes).
- The sanitizer rejects what only a hostile or broken sender sends and rewrites platform differences; the saved name is at most 200 bytes (a collision name can be longer, see the known limits); a zero-width joiner is refused with the rest of Cf.
- **File names (answer 3).** The four invisible fillers U+115F, U+1160, U+3164 and U+FFA0 are refused as `invisible`. A leading `.` is saved with a leading `_` (`.txt` becomes `_.txt`). NFKC is kept as a check and not as the saved form: the saved name is NFC.
- **Invisible characters (answer 2a, 2026-10-14).** Every Default_Ignorable code point of Unicode and U+2800 are refused as `invisible` in file names, and as `name-chars` in device names. This extends the four fillers of answer 3 to the whole set. The table `INVISIBLE_RANGES` in `reference.py` is written out by hand from the Unicode DerivedCoreProperties list, and is not taken from `unicodedata`.
- **Whitespace in file names (answer 2b, 2026-10-14).** A run of the whitespace code points listed under "File names" becomes one U+0020 before the checks, the trim and the byte cut, U+00A0 (no-break space) included. This widens the rule in one place: U+0009 to U+000D (tab, line feed, vertical tab, form feed, carriage return), U+0085, U+2028 and U+2029 in a file name are accepted as a space, where answer 2a refused them as `invisible`. Device names are not changed by this answer.
- **Reserved names (answer 2c, 2026-10-14).** `COM0` and `LPT0` are reserved, and so are `COM` and `LPT` followed by U+00B9, U+00B2 or U+00B3. These names are case-insensitive, with or without an extension, and are saved with a leading `_` (as in "Rewritten" above). `COM4` to `COM9` and `LPT4` to `LPT9` were already reserved in the reference and stay so. No other name changes.
- **Empty after the cut (answer 8 applied to the cut).** A name that is empty after trimming is refused as `empty`, and so is one that is empty after the byte cut or the rewrites above. An empty name is never saved.
- **Device ids (the owner's rule, 2026-10-14, narrowed the same day).** A hello or an advert whose device id equals this machine's own id is refused as `own-id`. An advert is refused for its own id (`own-id`), for the all-zero id and for a non-canonical `own_id`, a null one included (`device-id`), and for nothing else: it carries no key, so a paired id under another key is decided at the hello, and a paired id is never refused in an advert. A hello is refused unconditionally when it has no valid device id (`reveal-length` or `nonce-length`) and when its id is all zero (`device-id`), whether or not the machine has its own id or paired devices; while the machine's own id (a null one included), a paired id or a paired key is not canonical, every hello with a valid id is refused as `device-id`. A hello whose device id is already paired under another key is refused as `id-key-mismatch`; the same id under the key stored for it is allowed. The rule is on both pairing machines (the initiator at the responder's hello, the responder at the initiator's). To re-pair a device whose key has changed, the user removes the device first, and until then its pairing is refused. The reasons are part of the contract for ports: a port closes the connection and gives the same reason in its local log, and, for `id-key-mismatch` from the responder, sends nothing (see "The two machines").
- **Byte limits (answers 9 and 10), unchanged.** Zero-width joiners are refused with the rest of Cf. 1020 bytes on the wire; 200 bytes saved; 63 bytes for a device name.
- **The two-generals edge at the 2-minute window (answer 5), no rule change.** Each side's pairing window runs from its own start, so a pairing that ends near 120 seconds can be stored by one side while the other has already closed its window and discards it. Nothing is stored unless both said yes, so this is safe; the outcome is asymmetric by about one one-way latency. The consequence: the next transfer fails with an unknown key, and the user pairs again.
- **Cancel (answer 12).** A `cancel` with no transfer running is ignored, on the sender and on the receiver. A `cancel` during a transfer ends it, as described under "What each side does with each frame".

**Known limits, stated plainly:**
- **Case folding of ß.** The collision check compares names with `casefold`, which turns `ß` into `ss`: a `straße.txt` and a `strasse.txt` are treated as colliding, so the second is saved as `strasse (1).txt`. The usual volumes of macOS and Windows do not fold them that way, so a real folder would keep both. `unique_name` is a sanitizer-level check only and does not make a file exclusive: the volume decides which names are the same file, and the reference's `casefold` does not model every volume's rules (it keeps U+0131 apart from `I`), so `unique_name` can report a name as free that a volume treats as taken. A port must create the file exclusively (`O_EXCL` on macOS and Linux, `CREATE_NEW` on Windows), and on "already exists" it must choose the next free name and try again. The reference's `casefold` is a known limit: the casefold of ß and the case folding are documented limits, by the owner's answer.
- **Collision names can be longer than 200 bytes.** A collision name is the saved name with ` (n)` before its extension, so it can reach 207 bytes (a 200-byte name plus ` (9999)`; 204 bytes for the first nine collisions). The 200-byte limit leaves the room under the 260-character Windows path for the folder `Downloads\NotchMeow\` and for the suffix. A numbered collision name can contain two spaces where the stem ends in a space (`a .txt` becomes `a  (1).txt`); it cannot hide an extension.
- **Look-alike dots are kept.** The full-width full stop U+FF0E and the one-dot leader U+2024 are not `.` in NFC, so they are kept in the saved name (`．txt`, `․x`). NFKC maps them to `.` for the checks (so a name made only of them is refused as `empty`), but on macOS and Windows they are not hidden files, so they do not hide anything.
