# NotchMeow — guide for AI coding agents

NotchMeow is a native macOS app (`NotchBuddy/`); `windows/` is the Tauri version for Windows and Linux. Shrimpy and Momo, two animated cat heads living in the MacBook notch, show AI coding agent sessions (Claude Code, Gemini CLI, Antigravity and more) and a few integrations, and let the user approve, answer, chat and drop files from the notch.

## Where things are
- `NotchBuddy/Sources/App/` — all Swift code. `NotchBuddy/Resources/sounds/` — NotchMeow's own WAVs (one per slot), built from CC0 clips by `tools/sounds/build_pack.py` and credited in `docs/SOUND-CREDITS.md` (Coucou's are reserved and must never be added back). `NotchBuddy/project.yml` — XcodeGen project (never edit the `.xcodeproj` by hand).
- `NotchBuddy/Sources/App/PillCatalog.swift` — single source of truth for all declared pills (workspace tools, agents, AI providers, services). Every pill ID, color, category and subtitle lives here.
- `NotchBuddy/Sources/App/ShortcutLogic.swift` — every keyboard shortcut on the Mac: the global actions and their defaults, stored values and their validation, the island's own keys. Pure Foundation, tested by `scripts/test-shortcuts.sh`; `HotKeyCenter.swift` registers the global ones with Carbon (`docs/SPEC.md` §13). The Windows and Linux app has none.
- Settings on the Mac (`docs/superpowers/specs/2026-10-17-settings-restyle-design.md`): six pages (General, Agents, AI and chat, Services, Cat, Devices) and their tabs (General: General, Shortcuts; AI and chat: Your AI, Keys, Local models, Sidekick, Companion; Cat: Look, Outfits, Personality, Agents' cats) in `SettingsRoute.swift` with `migrate` for old `settingsSection` tags and `settingsTab.<page>`; the widths in `SettingsLayout.swift` (415 × 420 minimum, icon sidebar under 600, a 640 pt column); the drafts (`SettingsDraftBook`, `SettingsDrafts`), status words (`SettingsStatus`), the Sidekick tab's rules (`SettingsSidekick`) and the AI rows with Make main (`SettingsAI`) are pure. `SettingsMap.swift` and `tests/fixtures/settings/controls.json` name every control's home and stored keys; `scripts/test-settings-map.sh` fails if a stored key is lost, renamed or homed twice. The kit (`SettingsShell`, `SettingsPage`, `SettingsCard`, `SettingRow`, `SwitchRow`, `KeyRow`, `StatusChip`, `WrapRow`, `PathDisclosure`, `HelpText`, `SettingsTabBar`, `SettingsBanner`) keeps words whole and buttons untruncated at any width; the page views (`Settings{General,Agents,Services,AI}Page.swift`, `SidekickSettingsView`, `CatSettingsView(tab:)`, `ShortcutsSettingsView`, `DevicesSettingsView`) take plain values; `SettingsSections.swift` and `SettingsController.swift` are the app's side of the pages; `SettingsView.swift` (the shell, which reads `AppState` and the Keychain for its drafts) and `SidekickSettingsView.swift` (which reads `AppState`) are the two other Settings files that do. `bash scripts/render-settings.sh` draws every page and tab at 415/720/1100 in dark or light (`--appstore`, `--stress`, `--states`, `--kit`) without the app; `scripts/check-settings-render-private.sh`, `test-settings-{rules,map,ai,contrast,wiring}.sh` are its tests. The never-restyle rule is lifted for Settings only.

## Rules
- Swift 6, SwiftUI + AppKit. No third-party dependencies unless truly unavoidable. The character is drawn in code (`Canvas` + `TimelineView`), no Rive/Lottie/images.
- Secrets live in the Keychain, never on disk or in git.
- No telemetry. Network calls only to services the user configured.
- Never block Claude Code: if the app doesn't answer, the hook exits immediately.
- Never overwrite `~/.claude/settings.json`: dated backup, merge, show the diff, write only after the user confirms.
- Never send an email or approve a Claude Code or Codex permission without an explicit click.
- Performance: 0 % CPU when the island is hidden. One documented exception, the desktop cat's light checks, only while the cat is out: on Windows a cursor read at about 10 Hz (60 Hz near the cat) and a click-through check every 16 to 100 ms, on Linux no cursor read (the input region is the shape), on the Mac the mouse-moved monitor; on Windows and Linux a screens/fullscreen look at 2 Hz. They stop when the cat is home, asleep (the hover check that wakes it excepted), locked or the display is off; a fullscreen app hides it (no drawing, window hidden) while the checks keep watching for its end. They cost under 1 % of a core when idle (`windows/README.md`, `docs/SPEC.md`).
- Keep the bundle identifiers `io.github.aikusan.notchmeow` and `io.github.aikusan.notchmeow.store` (Keychain items, preferences and permissions depend on them). Identity and contract strings (`nm-hook`, `nm.sock`, `notchmeow-hook`, `nm_kind`, `nm_agent`, the `NotchMeow` folders) are renamed together or not at all; a half-rename makes hooks fail silently.
- Licensing: the code is MIT and keeps Louis Raillé's notice. Never reintroduce Coucou's reserved assets (the names Coucou and Mochi, the Mochi design, its icons, sounds, captures or media). NotchMeow's own names, cats, icons and sounds are covered by LICENSE-ASSETS.md.
- Never restyle what already ships (pills, cards, Settings, chat…): existing views stay exactly as they are in `main`, which is the App Store build. Change the look of an existing view only when explicitly asked.
- Pill IDs are stable contract values (Keychain, UserDefaults, hook routing): never rename an existing pill ID.
- Cat IDs (`shrimpy`, `momo`, `ginger`, `midnight`, `latte`, `patches`, `blue`, `snow`, `oreo`, `mocha`, `silver`, `cloud`, `leo`, `button`, `puff`, `noodle`) are frozen the same way, because they are stored in settings. An unknown stored ID falls back to `shrimpy`.
- **macOS is the primary platform.** When the two apps' plans differ, the Mac gets at least what Windows/Linux gets: features, dev tools and polish. Platform-only extras (like Windows OCR) are fine.
- New views follow the existing app style. `design/prototype/notchmeow.html` is the reference for new character work, not a reason to change existing views.

## Working with AI agents
- **Haiku 5.5 first; Sonnet 5.5 only when the task needs it** (owner's rule, 2026-10-12). Never Opus or Fable, with one exception: **implementation plans are written on Opus 5.5** (`claude-opus-5-5`; owner's rule, 2026-10-17, for better plans). Every subagent and worktree session starts from Haiku 5.5 (`claude-haiku-5-5`) and moves to Sonnet 5.5 (`claude-sonnet-5-5`) only when at least one of these holds; the brief or the ledger names which one:
  1. platform APIs or concurrency the task must design rather than copy (AppKit windows and panels, Carbon hot keys, Swift 6 actors, Tauri/Rust windowing, layer-shell);
  2. debugging a failure whose cause is unknown, or a task Haiku has failed twice;
  3. design work: a spec or an architecture question (a plan draft with its dry run runs on Opus 5.5, below);
  4. a whole-branch final review, or a security or privacy review;
  5. controlling a worktree session that runs an app plan with hard integration or many cross-task interfaces.

  Everything else runs on Haiku 5.5, at the effort the task needs: **low** for lookups and mechanical edits, **medium** for transcribing given code, fixtures, docs and CI YAML, **high** for multi-file coding, task reviews and visual checks.

  | Work | Model, effort | Agent |
  |---|---|---|
  | Transcribing a plan task whose full code is given, fixtures, docs, CI YAML | Haiku 5.5, medium | `nm-implementer-light` |
  | Normal multi-file coding | Haiku 5.5, high | `nm-implementer` |
  | Hard integration, platform APIs, debugging, Haiku's third try | Sonnet 5.5, high | `nm-implementer-deep` |
  | Task reviews and fix re-reviews | Haiku 5.5, high | `nm-reviewer` |
  | Whole-branch final review | Sonnet 5.5, high | `nm-reviewer-deep` |
  | Lookups, read-only questions, simple research | Haiku 5.5, low or medium | any |
  | Specs, multi-source research | Sonnet 5.5, medium | any |
  | Implementation plans: drafts with their dry runs, and rewrites | **Opus 5.5**, high | any (pass `model: opus`) |

  The `nm-*` agents live in `~/.claude/agents/` (outside the repo) and pin the model, effort and skills. A session sees them after a restart. Without them, pass `model` to the Agent tool and put the skills in the prompt.
- **Coding subagents load skills:** `ponytail:ponytail`, `superpowers:test-driven-development` and `superpowers:verification-before-completion`, plus `superpowers:systematic-debugging` for hard work. Reviewers load `ponytail:ponytail-review`. Ponytail never cuts what a plan or spec explicitly asks for, nor tests, security or privacy rules.
- **Extra skills by kind of work** (owner's rule, 2026-10-17): Swift and Rust skills for coders, the silent-failure and test-gap agents beside the final review, `security-review` for privacy work, agent-safety skills for the chat rebuild, an accessibility audit before the Settings restyle, the launch checklist at relaunch, `cli-anything` instead of clicking through an app by hand. `ARCHITECT.md` has the table, and the list of skills never to load here (they push, publish, phone home, restyle by default, reverse-engineer, or write hooks and settings on their own).
- **Plans run in git worktrees**, one branch per plan. A second plan can run in parallel in its own worktree chat session. The main session coordinates, reviews and talks to the owner.
- **Worktree chat sessions follow the same rule**, never Opus or Fable (Opus 5.5 only for a session that writes an implementation plan):
  - Haiku 5.5 (medium) for docs-only or mechanical chores, plans whose tasks are given in full (contracts, fixtures, small fixes), and one small fix;
  - Haiku 5.5 (high) for plans that need some judgement but no platform design (the site, release scripts);
  - Sonnet 5.5 (high) only for app plans with hard integration, platform APIs, concurrency or many cross-task interfaces (trigger 5).

  A chip's first turn runs on the app default, and a model change applies from the next turn. So the chip only sets up and stops (its prompt carries the owner's advance approval of the brief); the main session then sets the session's model and effort and sends the controller brief. Every worktree session pings the main session with `SendMessage` at each checkpoint, at the end and whenever it stops, so the main session can double-check the work. `ARCHITECT.md` has the three steps.
- **Archive worktree sessions once they're no longer needed:** the branch is merged or dropped, the report has reached the owner, and nothing is pending. Archiving deletes the worktree folder, so first save its ledger, note any owed manual checks, and move the folder to the Trash. `ARCHITECT.md` has the steps.
- `ARCHITECT.md` holds the architecture map, the main flows and the agent workflow. Read it before planning.
- **Code questions:** ask the graphify graph in `graphify-out/` first (`graphify query "..."`), then read the files it points to. It's excluded from git locally; refresh it incrementally after big changes.
- **The Obsidian vault** (`~/Documents/Obsidian Vault`, rules in its own `CLAUDE.md`) is the shared record of decisions and session handoffs across Claude clients. At session start the main session reads its `Home.md`, the newest `03-Sessions/` note and `01-Projects/NotchMeow.md`; at a handoff it writes a `03-Sessions/` note, and it records each meaningful decision in `02-Decisions/`, linked from the project note. Worktree sessions and subagents only read it. Code questions go to the graphify graph, which is never exported into the vault. When a vault note disagrees with this repo, the repo wins and the note is flagged as stale.
- **Never push**, and commit only when the owner asks.
